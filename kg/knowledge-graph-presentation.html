03 — The Limitation

Knowing the node isn't
enough

Traditional Index Answers

  • Is "Oak" in the database?
  • Where does "Oak" appear?
  • How many times is "Oak" mentioned?

Knowledge Graph Answers

  • Oak is a tree (entity type)
  • Grows in temperate forests (context)
  • Related to furniture, paper, wine barrels
  • Found in North America, Europe, Asia
  • Sold via timber markets

Not just knowing the tree — knowing where it grows, where it's sold, and who depends on it.

04 — The Structure

Knowledge Graphs are
semantic networks

Every fact is a triple:
(Entity A) — [relationship] → (Entity B)

(Marie Curie) — [BORN_IN] → (Warsaw)
(Marie Curie) — [WON] → (Nobel Prize)
(Nobel Prize) — [AWARDED_BY] → (Swedish Academy)
(Warsaw) — [LOCATED_IN] → (Poland)

07 — The Old Problem

Why Knowledge Graphs
stayed niche

"Someone had to sit down and manually encode every entity, every relationship, every tuple. Domain experts. Hours of labeling. Expensive to build, expensive to maintain."
The problem

Manual Construction

Each triple (A, rel, B) required human curation. Ontologies took years to build. Freebase, Cyc, WordNet — massive team efforts.

The consequence

Limited Scale

Only well-funded organizations (Google, DBpedia) could build large KGs. The rest relied on keyword search and hoped for the best.

08 — The Breakthrough

Embeddings: the semantic
hash table

What Embeddings Do

  • Convert text → dense vector (e.g. 1024-dim)
  • Semantically similar text → nearby vectors
  • "King" − "Man" + "Woman" ≈ "Queen"
  • Relationships encoded in geometry

Why It Matters for KGs

  • Entities can be auto-clustered by meaning
  • Relationships inferred from vector proximity
  • No more manual tuple encoding per item
  • Scales to billions of documents
Hash table: key → bucket (exact match)
Semantic hash table: meaning → neighbourhood (fuzzy, contextual)
09 — The Unlock

AI makes KG construction
automatic

Step 01

Entity Extraction

LLMs identify key concepts, proper nouns, and domain objects from raw text automatically.

Step 02

Relationship Inference

Semantic understanding lets models infer how entities relate — without hand-coded rules.

Step 03

Graph Population

Triples are auto-generated and ingested into graph DBs like Neo4j at scale.

The #1 reason KGs weren't widely adopted — just dissolved.

10 — The Transformation

A document becomes
a universe of meaning

Before: Flat Document

  • Keyword matching only
  • No understanding of context
  • Search: "procurement" → all docs with that word
  • Lost: who, what, why, how things connect

After: Knowledge Graph

  • Key concepts extracted as entities
  • Relationships mapped explicitly
  • Query: "suppliers connected to delayed orders"
  • Found: chains of causality, not just keywords

The same document. Infinitely richer access.

11 — Modern Application

Knowledge Graphs
+ RAG

Vector RAG

Semantic Similarity

Find chunks that are semantically close to the query. Great for fuzzy, open-ended questions.

Graph RAG

Relationship Traversal

Navigate entity connections. Great for "who connects to whom," multi-hop reasoning, causal chains.

Hybrid

Best of Both

Vector retrieval surfaces candidates. Graph context enriches them. Reranker picks the best. Maximum precision.

14 — Tech Internals · Data Model

What actually lives in
Neo4j and Qdrant

Neo4j — Graph Store
Node Labels
:Document :Entity :Concept :Chunk
Relationship Types
MENTIONS RELATED_TO PART_OF DEPENDS_ON
Sample Cypher Query
MATCH (e:Entity)-[r:RELATED_TO]->(c:Concept)
WHERE e.name = "IMS"
RETURN e, r, c
LIMIT 10
Qdrant — Vector Store
Collection Config
collection: "rag_chunks"
vector_size: 1024
distance: Cosine
index: HNSW // fast ANN
Payload (Metadata) Schema
doc_id: "ltesms_v25"
chunk_id: "chunk_042"
text: "The device shall..."
entity_refs: ["IMS", "DUT", "SIP"]
neo4j_ids: [4821, 4822, 4830]

The entity_refs and neo4j_ids fields are the bridge — vector chunks know which graph nodes they came from, enabling cross-store joins at query time.
